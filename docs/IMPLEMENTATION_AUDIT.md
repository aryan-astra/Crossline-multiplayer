# Implementation audit before persistent multiplayer work

Audit date: 23 October 2026. This is a pre-change record of the integrated root application against the new master directive. It deliberately distinguishes inherited functionality from implementation still required. The directive calls the game FAULTLINE provisionally; the repository and previous explicit user name are Crossline. Naming is presentation metadata and should not cause a project rewrite.

## Inspection and evidence

Read the attached master directive, root package/configuration, game types, engine, navigation, loop, rendering entry points, client driver/menu, existing tests, and previous validation record. Inspected Git status before editing: no pre-existing changes were reported. Node.js on this machine reports 24.20.0. No supplied scripts, database migration, cloud command, or original prototype application was executed for this audit.

The integrated application is Next.js 16.3.8, React 19.2.6, strict TypeScript, Canvas 2D, npm, ESLint, Prettier, and Node's test runner. The package declares Node >=22 and <25; adopting Node 24's SQLite requires narrowing/documenting that supported runtime. Existing dependencies contain no database driver or WebSocket server. `next.config.ts` is empty configuration. Original extracted source trees remain local reference material and must stay preserved.

Previous `docs/VALIDATION.md` reports 17 passing rules tests, browser practice flows, and a production build on 22 October. Those are prior executed results, not newly rerun checks and not multiplayer evidence. They are a useful regression baseline. The new directive changes core rules, so tests asserting round termination, unrestricted military practice, and reset-on-exit money must change with their implementation.

## Concrete integration scope

The architecture is salvageable. Keep React/Next, maps, procedural Canvas rendering, seeded RNG, fixed-step helpers, collision, formation/milling, suitable interaction functions, and existing tests as regression material. The highest-risk assumption is single-player state ownership, not the choice of frontend framework.

The change must reach `src/game/types.ts`, `engine.ts`, `maps.ts`, `navigation.ts`, AI helpers, renderers, camera/input/HUD/menu callers, tests/fixtures, package scripts/runtime types, CI, ignore rules, environment examples, and engineering documentation. Add a server transport/protocol and persistence boundary. Avoid exposing the whole server world object blindly: session tokens, private account/ledger data, and server-only control state are not public snapshots.

Recommended local architecture: one custom Node HTTP process hosts Next and a bounded `ws` endpoint. It owns exactly two internal location coordinators exposed as one public world. Shared headless simulation performs all trusted outcomes. Browser code consumes public snapshots and sends validated intentions; cameras/settings remain client-local. SQLite stores durable accounts, guest-session hashes, progression, wallets, transactions, bets, global events/objective state and bounded checkpoints. Transient NPC positions/effects may regenerate after restart, as allowed by the directive. No room browser or private-room API is needed.

Before adding public economy actions, implement one transaction boundary that atomically records an operation key and all debit/credit/result changes. Starting life credits are not a transferable respawn profit source. Refresh/reconnect/location changes reuse identity and life state. A late duplicate objective input cannot award another capture. Role checks occur at action processing time, not just menu selection.

## Ordered acceptance gates

1. Build the shared authoritative state and protocol boundary; regress seeded initialization, movement, collision, actor authorization and fixed steps.
2. Introduce continuous objective phases, custody/death, eligibility and bounded resource/AI state; verify no global timer or per-browser world recreation controls the server.
3. Add SQLite migrations and atomic operation records; test restart recovery, session reconnection, duplicate payouts/grants and transaction rollback.
4. Connect independent clients to the same bots/objective/events; test stale inputs, invalid coordinates, forbidden actions, heartbeat expiry and slow receivers.
5. Integrate actual menus/HUD/interiors/cameras and two-location switching, then run desktop/touch browser tests and renderer/simulation/network benchmarks.
6. Update source, architecture, simulation, protocol, schema, economy, controls, validation and deployment documents to describe implemented behavior. Preserve this audit as the initial state rather than rewriting it to pretend missing systems already existed.

The audit does not certify new multiplayer, persistence, renderer capacity, Android hardware behavior, or cloud deployment. Those require implementation and executed tests.
