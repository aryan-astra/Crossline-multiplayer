# Deployment options

Checked 26 October 2026. This answers the current request for one public lobby where everyone joins the same authoritative world at no hosting cost. It does not promise unlimited players, continuous uptime or durable $0 hosting.

## One shared public world

All players must connect to one online server URL and choose the same city to share its map simulation. There is no random room allocation in the current server; Delhi and Paris are two location worlds with a shared economy. The existing admission ceiling is **64 connected members across the server**, including spectators. That is a safety bound, not a measured supported concurrency claim. The current benchmark covers up to ten humans with an adaptive bot population in one headless world, excluding transport, SQLite and rendering.

For the first public session, use one announced city and one server endpoint. Increase admission only after measuring both active cities, input acknowledgement latency, snapshot bytes, SQLite pauses and slow receivers under real connections. A future connected city world can divide computation into spatial zones while preserving shared authority and cross-zone actions; independent local browser simulations cannot supply that consistency. A massive continuously active lobby has no verified $0 hosting path today.

## Current $0 setup: run the Node server on the LAN

Use `npm run start:lan` for private-network play. For public hosting use online mode: set `PUBLIC_ORIGIN` to the HTTPS origin and run `npm run start:online`, with its separate database file. On Render, `RENDER_EXTERNAL_URL` already selects online mode for the existing `npm start` configuration. Do not put a public tunnel in front of LAN mode. `ONLINE_URL` can link a LAN title screen to an independently deployed public game. No public server was provisioned in this pass.

The existing Node server is the no-extra-hosting-cost option when the user has a machine to run it. Set `HOST=0.0.0.0`, start the app, and join from other devices on the LAN using the host's address. It remains available only while that machine and network are up. Public exposure adds TLS, firewall, backup and availability work.

For a **temporary public play session from your own computer**, run the existing app in online mode and front it with a Cloudflare Tunnel. The tunnel forwards an HTTPS/WSS public hostname to the local HTTP server; `server.ts` already serves both the app and `/socket` on the same listener. Set `PUBLIC_ORIGIN` to the exact public HTTPS origin and use `npm run start:online`, which selects the separate online SQLite file. Do not expose LAN mode: online mode enables public-origin checks and secure guest cookies. Quick Tunnels need no account or domain, but their random hostname changes each run, anyone holding the URL can reach the service, and Cloudflare labels them development/testing only. Stop the tunnel and server after the session; the host PC and home internet must stay on. For a stable hostname, a named tunnel needs a domain routed through Cloudflare, so it is not automatically zero-cost. Do not share a tunnel URL until the production build is ready and the public endpoints have been reviewed. [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), [Tunnel setup](https://developers.cloudflare.com/tunnel/get-started/).

For an eventual cloud-native deployment, treat a Cloudflare Durable Objects port as a bounded-budget target, not a drop-in or unlimited-free deployment. It needs Worker/DO transport and storage changes, durable state recovery, and measured limits for active time, sockets and requests. Current Cloudflare free allowances can be exceeded by continuous location ticks or input traffic; see [deployment research](DEPLOYMENT_RESEARCH.md).

## Optional public resettable demo

Render Free **web service** is a possible public, resettable demo. The root [render.yaml](../render.yaml) defines one Node web service, the existing Next + `ws` + SQLite app, health check and the Free plan. It sets `HOST=0.0.0.0`, `NODE_VERSION=24.20.0`, `DATA_FILE=/tmp/crossline.sqlite`, builds with `npm ci --ignore-scripts && npm run build`, and starts with `npm start`; Render supplies `PORT`, which the server already reads. It requests no database, disk or paid custom domain. Render provides an `onrender.com` hostname and managed TLS. Render's Blueprint reference lists Free at 0.1 CPU and 512 MB RAM; no free-tier load/endurance measurement has been run, so this configuration does not promise stable 30 Hz simulation under active play. Free capacity and account availability are also controlled by Render, so the file cannot guarantee that a Free service can be provisioned. See [Render Free services](https://render.com/docs/free), [Node version selection](https://render.com/docs/node-version) and [Blueprint specification](https://render.com/docs/blueprint-spec).

To deploy it, push the file to the Git branch you want to serve, then in Render choose **New > Blueprint**, connect the repository and select that branch. Review the pending resources and confirm it shows only the one Free web service before choosing **Apply**; that initial Apply creates and deploys the service. `autoDeployTrigger: 'off'` prevents code commits from automatically deploying. Blueprint Auto Sync is a separate dashboard setting: set it to **No** in Blueprint Settings for manual configuration syncs too. For later code updates, use the service's **Manual Deploy > Deploy latest commit**. [Create a Blueprint](https://render.com/docs/infrastructure-as-code), [deploy behavior](https://render.com/docs/deploys).

This is a **demo, not durable public-world hosting**. Render Free spins down after 15 minutes without inbound HTTP or WebSocket messages, may restart services at any time, and its filesystem is ephemeral. `DATA_FILE` is deliberately under `/tmp`; a restart, spin-down or deploy loses the SQLite database: guest identities, credits, market state and world checkpoints reset. Active game clients send input messages, but the simulation cannot be relied on to keep running when nobody is playing. Free services share 750 instance hours per workspace each month; outbound bandwidth and build minutes are also capped by workspace usage. With no payment method, exceeding included usage suspends services or prevents builds rather than keeping them available. Do not use this path where progress, an always-running world or production uptime matters. [Render Free limits](https://render.com/docs/free), [outbound bandwidth](https://render.com/docs/outbound-bandwidth).

The server reads Render's `RENDER_EXTERNAL_URL` automatically for HTTPS origin checks and Secure guest cookies. On another reverse proxy, including Cloudflare, set `PUBLIC_ORIGIN` explicitly; do not infer the public origin from edge or client-forwarded headers.

## If continuous play and retained SQLite data are required

There is no provider-supported way to promise an always-on, durable public service at exactly $0 with no existing hardware and no account/availability conditions. The closest cloud candidate is an **Oracle Cloud Infrastructure Always Free VM**, running this same Node process with `DATA_FILE` on its boot volume. The offer includes up to 2 Ampere OCPUs, 12 GB RAM and 200 GB combined block-volume storage. However, compute must be in the account's home region and may be unavailable; Oracle says most sign-ups require a phone number and credit card, and idle Always Free compute can be reclaimed. This is therefore conditional, self-managed and not an uptime guarantee. A credit card is not a usage charge, but it is still a registration requirement for most people. [Oracle Free Tier](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm), [Always Free resources and reclamation rules](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

If an eligible VM is available and its terms are acceptable, provision only Always Free resources, cap the tenancy with quotas, install a tested Node 24.x runtime, build the app, run `npm start` under a restart manager, and keep `DATA_FILE` on the durable boot volume. Bind publicly only behind firewall rules and HTTPS/WSS. A public DNS name and certificate must also be available without charge for this to remain a literal $0 deployment; do not assume one is included with the VM. Back up SQLite/WAL safely and test restart recovery. Oracle capacity, account approval, reclamation and network setup make this a best-effort option, not a service that can be promised to every user.

Existing always-on hardware can also run the app for $0 in additional hosting fees if its owner supplies uninterrupted power, internet, public reachability and HTTPS/WSS. It is offline whenever that host or connection is offline, and exposing a home machine publicly needs deliberate firewall and security work. Do not assume this hardware exists.

## Why other free hosting paths do not fit unchanged

- **Static hosting (including Cloudflare Pages/Workers Static Assets):** can serve an intentionally exported frontend only. This project uses a custom Next server, WebSockets, a 30 Hz authoritative simulation and Node's filesystem SQLite; static delivery cannot run those. The browser must not become authoritative to make a static deploy seem viable.
- **Vercel Functions:** current docs support WebSockets on all plans, and `ws` is supported. However, each socket closes when its function reaches the configured maximum duration (Hobby max 300 seconds); reconnects may land on a different function instance. A shared external authority and persistent store are needed, and the standalone `server.ts`/SQLite process does not deploy unchanged as a Vercel Function. Thus Vercel is not a drop-in host for the current continuously ticking world, even though WebSockets themselves are supported. [Vercel WebSockets](https://vercel.com/docs/functions/websockets), [Function duration limits](https://vercel.com/docs/functions/limitations).
- **Cloudflare Workers / Durable Objects:** free Workers allow 100,000 requests/day and 10 ms CPU per invocation; free SQLite-backed Durable Objects allow 100,000 requests/day, 13,000 GB-s/day, 5 million rows read/day, 100,000 row writes/day and 5 GB storage. This app's `node:sqlite` import is only a Workers compatibility **stub**; it is not the local SQLite database API. The current custom HTTP server, `ws` transport and `DatabaseSync` store cannot be deployed as-is. A port must replace HTTP/upgrade handling with Worker/DO handlers, `ws` with the DO WebSocket API, and `DatabaseSync` with DO SQL storage, while restoring world state across hibernation. A continuously scheduled 30 Hz simulation prevents hibernation; two separate continuously active DOs allocated 128 MB each would consume about 22,118 GB-s/day before requests, above the 13,000 free daily allowance. Even one active player sending this app's 20 Hz inputs for a full day would use about 86,400 DO requests/day after Cloudflare's 20:1 WebSocket message billing ratio; two such players exceed the 100,000 daily allowance before other calls. These are quota calculations, not measured usage. A port would need explicit budgets for object count, active time and requests; it is not a drop-in or unlimited free host. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [DO WebSockets and hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [Workers `node:sqlite` compatibility flag](https://developers.cloudflare.com/workers/configuration/compatibility-flags/).
- **Netlify Functions:** the Free plan's 300 monthly credits are consumed by production deploys (15 credits), bandwidth (20/GB), compute (10/GB-hour) and requests (2/10,000). No claim is made here about Netlify WebSocket support. The current Node/SQLite authority needs a persistent/shared backend adaptation. [Netlify pricing](https://www.netlify.com/pricing).
- **Render Free PostgreSQL as a replacement:** requires a storage adapter and Render says its free PostgreSQL database expires after 30 days, so it does not provide durable production persistence. [Render Free limits](https://render.com/docs/free).

Keep runtime data out of Git. No account, deployment, paid service or payment integration was created.
